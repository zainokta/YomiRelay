# YomiRelay MVP Design

**Date:** 2026-08-28

## Goal

YomiRelay is a local-first, cross-platform application that relays dialogue from installed Ren'Py Steam visual novels into a browser as normal selectable HTML text. It is deliberately not a dictionary, translator, OCR tool, browser extension, or process hook. Its only MVP source is a generated Ren'Py callback hook.

The application binds HTTP to `127.0.0.1:17321` and UDP to `127.0.0.1:17322` by default. Environment variables `YOMIRELAY_HTTP_ADDR` and `YOMIRELAY_UDP_ADDR` override these values; callers remain responsible for keeping overrides local.

## Chosen approach

Use a small Go application based on the standard library for HTTP, UDP, Server-Sent Events, static serving, filesystem operations, and Steam KeyValues parsing. Implement only the KeyValues/VDF subset needed for Steam library discovery rather than adding a VDF dependency.

Use `golang.org/x/sys/windows/registry` only in a Windows build-tagged Steam locator, since Go's standard library does not expose the Windows registry. This is the sole planned backend dependency.

Use a pinned Octane/Vite TypeScript SPA. The initial pinned frontend versions are `octane@0.1.48`, `@octanejs/vite-plugin@0.1.48`, `vite@8.2.2`, and `typescript@7.0.2`, verified as current npm releases on 2026-08-28. `package-lock.json` is committed. Before frontend code is written, the exact needed Octane lifecycle/list/event APIs will be verified in the current official documentation; no undocumented compiler behavior will be used.

## System architecture

```text
Steam install files                  Ren'Py game process
       |                                      |
       v                                      v
Steam discovery -> Ren'Py detector      generated .rpy callback
       |                                      |
       +-- discovered game registry          | UDP JSON, loopback only
                                              v
                                     UDP receiver and validator
                                              |
                                              v
                      dialogue history / activity store / SSE broadcaster
                                              |
                    +-------------------------+-------------------------+
                    v                                                   v
              REST API                                            SSE endpoint
                    |                                                   |
                    +------------------ Octane SPA ---------------------+
                                              |
                              ordinary selectable DOM text, lang="ja"
```

The backend owns all discovered game paths and all filesystem writes. The browser sends app IDs only and cannot select an arbitrary filesystem path. The frontend knows a normalized dialogue model, not Ren'Py payload details, leaving a narrow seam for future sources that can produce the same model.

## Backend components

### Platform and Steam discovery

`internal/platform` defines `SteamLocator` and selects platform implementations using Go build constraints:

- Linux probes `~/.local/share/Steam`, `~/.steam/steam`, `~/.steam/root`, and Flatpak Steam at `~/.var/app/com.valvesoftware.Steam/.local/share/Steam`.
- macOS probes `~/Library/Application Support/Steam`.
- Windows reads the Steam registry key through the isolated registry dependency, then tries `C:\Program Files (x86)\Steam`.

`internal/steam` accepts roots, adds each root's main library, parses `steamapps/libraryfolders.vdf`, deduplicates configured libraries, and enumerates only `steamapps/appmanifest_*.acf` in each library. It returns app ID, name, install directory, and the full path under that library's `steamapps/common`. It never scans arbitrary directories or the whole disk.

The internal VDF parser is a lexer and recursive object parser for the Steam subset: quoted keys/values with escaped quotes and backslashes, braces, whitespace, and line comments. It does not attempt to be a general Valve KeyValues implementation. It has fixtures covering multiple libraries and manifests.

`internal/games` enriches Steam installations with engine detection and presentation state. Ren'Py detection is based solely on filesystem layout: a `game` directory plus one or more corroborating signals such as a root `renpy` runtime directory, `game/*.rpa`, `game/*.rpy`, or known runtime files. A name is never used as a signal. The registry is refreshed at startup and on the explicit API refresh operation.

### Ren'Py hook management

`internal/hook` creates only `<install>/game/_yomirelay_hook.rpy`. The generated template begins with exactly:

```text
# Generated by YomiRelay
# DO NOT EDIT
```

Install rejects non-Ren'Py or unknown games. If the target exists, it must be a regular file containing both marker lines before it is updated. A symbolic link is refused. New content is written to a temporary file in the target directory and atomically renamed where the operating system permits. Removal also refuses symbolic links and deletes only a regular file whose contents include both markers. An unmanaged conflict produces `HOOK_FILE_CONFLICT`; an unowned file is never overwritten or deleted.

All hook paths are constructed with `filepath` from a discovered installation record, never from browser input. App IDs are decimal-only and must match a registry record. The target directory must be the resolved game directory within the discovered install root.

### Generated Ren'Py hook compatibility

The hook uses documented `config.all_character_callbacks`, appended during init Python, and a callback accepting `event`, `what`, `start`, and `**kwargs`. Official current Ren'Py documentation guarantees `what` and says `show` is called before every dialogue segment. It does not guarantee a speaker parameter.

On a `show` event whose segment starts at zero, the hook transmits exactly one normalized event for the statement. This prevents duplicate packets for `{w}` and `{p}` segments. A statement containing pauses is relayed in full at its first displayed segment; that trade-off favors one browser entry per say statement. The text cleaner removes only brace-delimited constructs that begin with an ASCII tag name or slash followed by an ASCII tag name, preserving Japanese text, punctuation, kana, and kanji. It leaves unrecognised braces intact.

The hook builds one small UTF-8 JSON datagram with standard `json`, `socket`, and `time`; it sends to `127.0.0.1:17322` through a non-blocking UDP socket and silently discards every exception. It makes no HTTP request, shell call, retry loop, acknowledgement wait, external-package import, or user-visible error. It reads optional `who` from callback keyword arguments when a particular Ren'Py build supplies it, otherwise omits `speaker`. Capture must still work with no speaker.

### Dialogue, receiver, and events

`internal/dialogue` defines:

```go
type Dialogue struct {
    GameID    string    `json:"gameId"`
    GameName  string    `json:"gameName"`
    Speaker   string    `json:"speaker,omitempty"`
    Text      string    `json:"text"`
    Timestamp time.Time `json:"timestamp"`
}
```

Its concurrency-safe in-memory store keeps the latest 1000 entries per game and exposes per-game reads/clears. It records `lastSeen` when a valid event arrives; a game is active for 30 seconds after that point. No persistence or database is introduced.

`internal/receiver` binds a UDP socket only to its configured address, uses a fixed maximum datagram size, accepts UTF-8 JSON only, requires schema version `1`, and requires non-empty game ID, game name, text, and a valid Unix-second timestamp. Invalid version, malformed JSON, invalid UTF-8, missing fields, invalid timestamps, and oversize packets are logged and discarded without terminating the listener.

`internal/events` publishes normalized dialogue to independent SSE subscribers. Each subscriber has a small bounded queue and its own writer loop. A full queue disconnects that subscriber, so neither it nor a stalled browser can block UDP ingestion or another browser. Events are sent as a named `dialogue` event with JSON data including `gameId`.

### HTTP API and static serving

`internal/api` owns routing, JSON encoding, error envelopes, and HTTP tests. Endpoints are:

- `GET /api/games`
- `POST /api/games/{appId}/hook`
- `DELETE /api/games/{appId}/hook`
- `GET /api/dialogues?gameId={appId}`
- `DELETE /api/dialogues?gameId={appId}`
- `GET /api/events`
- `GET /api/health`

A refresh action is represented by `GET /api/games?refresh=1`, avoiding an extra unrequested endpoint. It triggers a new discovery pass before returning. All errors use:

```json
{"error":{"code":"MACHINE_READABLE_CODE","message":"Human-readable explanation."}}
```

The server responds with appropriate 4xx errors for unknown app IDs, invalid app IDs, unmanaged hook files, invalid dialogue query parameters, and unsupported methods. It reports a concise 5xx JSON error and logs unexpected backend failures.

`internal/web` embeds `all:static` using `embed.FS`, serves hashed Vite assets, and falls back to `index.html` for SPA navigation while keeping `/api/` separate. Vite builds to `internal/web/static`, allowing the production binary to contain all frontend assets and need neither Node.js nor npm at runtime.

## Frontend behavior

The client is a single Octane application mounted through documented `createRoot`. It uses `.tsrx` components where markup is present and keeps REST calls and EventSource ownership in small API modules.

Games is the initial section and shows detected Ren'Py games only. Each card shows name, Steam app ID, install path, engine detection, hook status, active/inactive state, and last-seen time. It provides Refresh/Rescan, Install Hook, Remove Hook, and Open Reader. Successful installation shows the explicit notice: **Restart the game to activate the hook.**

Reader has a selected-game control, fetches that game's history when opened, and consumes a single shared dialogue stream outside individual line components. It filters by game ID before updating UI state. Each entry uses normal light-DOM elements such as:

```html
<article class="dialogue">
  <div class="speaker">林黙</div>
  <div class="dialogue-text" lang="ja">ご、ごめん。僕はただ……</div>
</article>
```

It does not use canvas, SVG text, images, character-per-span markup, inaccessible shadow DOM, or any Yomitan API. The dialogue body is an ordinary selectable text node so browser extensions can inspect it normally. The Reader has Clear History. When the scroll container is near the bottom, new entries auto-scroll; otherwise the view remains still and exposes Jump to latest.

The UI is compact, dark-mode friendly, and optimized for a side-by-side visual-novel setup rather than elaborate visual effects.

## Development and production workflow

`dev.sh` and `build.sh` start with `#!/usr/bin/env bash` and `set -euo pipefail`, derive the repository root from their own location, validate `go`, `node`, and `npm`, and reject Node versions older than 22.22.2 with the installed version shown.

Both scripts run `npm ci` only when `frontend/node_modules` is absent, preserving quick restarts. `dev.sh` starts `go run ./cmd/yomirelay` and `npm run dev` concurrently, prefixes output, handles partially-started child processes, cleans up on `EXIT`, `INT`, and `TERM`, and exits nonzero after stopping the other child if either one fails. Vite proxies relative `/api` and EventSource requests to `http://127.0.0.1:17321` in development.

`build.sh` builds Vite assets into `internal/web/static`, runs `go test ./...`, then produces `dist/yomirelay` and prints its path. The executable serves the embedded application at the configured HTTP address.

## Test and validation strategy

Every backend slice begins with a focused failing test, is followed by the smallest implementation, then runs its targeted test and `go test ./...` before its logical commit. Tests use temporary directories and committed fixtures; they never require a real Steam installation or a running game.

Required coverage includes VDF parsing, manifest parsing, multiple libraries, positive and negative Ren'Py detection, generated hook content, managed updates, unmanaged conflicts, safe removal, UDP valid/malformed/version rejection, Japanese UTF-8 round trips, history capacity and game isolation, SSE fanout, API unknown-ID rejection, and input/path traversal protection. An API test covers backpressure behavior without allowing a slow client to stop publication.

Before completion, frontend build, backend tests, production binary build, and a production HTTP smoke test run successfully. README includes the complete manual acceptance procedure: development startup, discovery, hook creation, game restart, live Reader updates, Yomitan's normal browser behavior, scroll preservation, backend-offline gameplay safety, resumed reception, and safe hook removal.

## Non-goals

This MVP excludes OCR, screenshots, Wayland/X11 capture, process scanning or injection, clipboard monitoring, Textractor, translation, LLM calls, dictionary/Yomitan APIs, furigana, Anki, vocabulary tracking, accounts, authentication, cloud sync, remote access, persistence, Steam Web API, game launch, arbitrary patching, and non-Ren'Py extraction.
